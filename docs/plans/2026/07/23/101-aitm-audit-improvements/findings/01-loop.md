# Findings — loop/

> Raw report from parallel audit agent. Scope: `packages/aitm/src/loop/` (12 modules + tests, cross-module contracts verified).

## Bugs / correctness

- [severity: high] [category: bug] `take-over-flow.ts:228-236` — a `'no-changes'` WorkerResult from the CI-fix pass is unhandled (only `'blocked'`/`'error'` are checked), so it falls through to `pushedSomething = true`, force-pushes nothing, and re-loops up to `maxIterations` (30) coding-tier LLM passes on a red PR — the exact burn ci-fix.ts:194-201 explicitly blocks on ("'no-changes' here is a contradiction"); add the same guard.
- [severity: med] [category: bug] `ci-fix.ts:179` (with `src/state/pr-context-store.ts:42-44`) — `runFixSession` calls `prContext.clear(pr)`, which `rm -rf`s the whole `pr/<n>/` dir *including* `addressed_threads.json`, silently wiping the addressing-reviews dedup that stage-handlers.ts:240-244 depends on for loop termination; after a CI failure mid-review-cycle, replied-but-unresolved threads are re-fed to the Reviewer (duplicate replies) — clear only the `ci/`/`comments/` subdirs.
- [severity: med] [category: bug] `self-review.ts:162-177` — a Worker `'error'` result (provider crash, step timeout) with verify green-or-unrun returns `{ kind: 'clean' }` and logs "nothing to fix": an errored review pass is indistinguishable from a genuinely clean diff, defeating the pre-PR gate; surface `worker.kind === 'error'` as its own outcome (or `unclean` with the error).
- [severity: med] [category: bug] `run-loop-adapter.ts:1140-1183` — `await discoverSpecialists(input.cwd)` (line 1142) sits *outside* the try/catch, and the roster announce at 1177 is `void ...then()` with no `.catch`: a `loadAgents` rejection (fs permission, malformed agent file) is an unhandled promise rejection AND the memoized rejected `specialistsPromise` makes every later `await specialistRoster()` (line 1402) throw, blocking every subsequent worker pass for the rest of the run; wrap discovery in the try and add `.catch`.
- [severity: med] [category: bug] `work-loop.ts:1096-1105` vs `stage-handlers.ts:158` — the prPerTask `autoMergeFlow` ignores `adminMerge` on a `CiFailed` poll timeout (the throw propagates → group blocked) and applies no `maxCiFixAttempts` budget (exactly one fix pass then throw), diverging from the stage machine's documented `--admin` timeout-override and issue-#128 cap; route both modes through one policy.
- [severity: med] [category: bug] `work-loop.ts:395,445` + `stage-handlers.ts:155` — `signal` is never threaded into stage handlers, `waitForChecks` (polls up to 2h, github-client.ts:94), or the 2-minute `REVIEW_COMMENTS_GRACE` sleep; `WorkLoop.run` only checks abort at batch boundaries after `Promise.allSettled`, so a single SIGINT can take *hours* to yield `cancelled` — pass the signal into `StageDeps`/`waitForChecks`/sleep.
- [severity: low] [category: bug] `take-over-flow.ts:211,228` — `ciStatus === 'cancelled'` is dead code: `observeCheckStatus` returns `CiResult.state`, which is `CiState = 'success'|'failure'|'pending'` (github-client.ts:109), never `'cancelled'`; and an unexpected `'pending'` silently burns a cooldown iteration doing nothing — type the variable as `CiState` and handle `'pending'` explicitly.
- [severity: low] [category: bug] `take-over-flow.ts:167-171,312` — iteration accounting is inconsistent: a first-iteration happy-path break reports `iterations: 0` on `merged`, while merged-after-exhaustion reports `maxIterations`; blocked branches mix both conventions.
- [severity: low] [category: bug] `take-over-flow.ts:186-193` — `reviewGraceDone` fires only once per flow; review bots that re-review after a CI-fix push re-greens are merged past without the grace window that exists precisely for them.
- [severity: low] [category: bug] `take-over-flow.ts:197,239-257` — no addressed-thread dedup (no equivalent of stage-handlers' `freshThreads`): a replied-but-unresolved thread is re-fed to the Reviewer on every iteration, up to 30 duplicate passes/replies on `aitm merge-pr`.
- [severity: low] [category: bug] `stage-handlers.ts:155` — the 2-minute grace sleeps on *every* pass through waiting-ci (each ci-fix loop-back and each resume re-entry), unlike take-over's once-guard — pure added latency per fix cycle.
- [severity: low] [category: bug] `run-loop-adapter.ts:1539` — `openPr` pushes with plain `git push -u origin <head>`; a resumed group whose branch was locally rewritten (a prior ci-fix rebase whose push failed) fails the plain push and blocks the group, while every other push path uses `--force-with-lease`.
- [severity: low] [category: bug] `run-loop-adapter.ts:693` — `PlanGraph.validate(groups)` on a resumed (possibly corrupted) state.json throws out of `runLoopAdapter` as an unhandled exception instead of a graceful `{ kind: 'blocked' }`.
- [severity: low] [category: bug] `ci-fix.ts:383,391` — a second-attempt non-conflict `continue` failure aborts with `manualReason` built from the *first* rebase's stderr, reporting a stale error to the operator.

## Resource cleanup

- [severity: med] [category: resource] `run-loop-adapter.ts:639-642,761-767` — `mcp.close()` runs only when `mcpConnected === true`: a `connectAll()` that throws *partway* (some stdio children already spawned) never sets the flag, so the finally skips close and the connected transports/child processes leak on normal (non-abort) unwinding; also a `seams.makeMcp`-supplied manager is never closed. `close()` is documented idempotent — call it unconditionally in the finally.
- [severity: med] [category: resource] `run-loop-adapter.ts:1189,1200,1514,1776` — `workerHandles` / `ciFixHandles` retain full `ModelMessage[]` conversations per group for the whole run and are never pruned when a group reaches a terminal stage; a long many-group run accumulates every conversation in memory — delete on merged/blocked.
- [severity: low] [category: resource] `run-loop-adapter.ts:631-632` — `reapOnAbort`'s `void mcp.close()` floats with no `.catch`; an abort-time close rejection becomes an unhandled rejection during shutdown.
- [severity: low] [category: resource] `ci-fix.ts:378-381` — `abortAndBlock` ignores a failed `git rebase --abort`; the checkout is then left mid-rebase and the next fix session's Worker edits a mid-rebase tree with no detection — check the abort's exit code and fold it into the blocked reason.
- [severity: low] [category: resource] `run-loop-adapter.ts:1012` — `plannerRecorder?.end()` is skipped when `runPlanner` throws (only the heartbeat is in the finally), leaving a dangling open transcript for a stage documented as never-resumed; same skip pattern at 1349/1515/1773 (arguably intentional for resumable stages — the planner one is not).
- [severity: low] [category: resource] `work-loop.ts:384,458` — `groupStartedAt` entries are never deleted after a group finishes (bounded by plan size; minor).

## Architecture

- [severity: high] [category: arch] `run-loop-adapter.ts` (2049 LOC) — at least six reasons to change in one module: tool resolution/partial-fill (356-400, 1954-2022), MCP deferred-tool mounting (1853-1951), branch naming (774-832), planner wiring + scout survey (874-1026), budget check (1033-1058), the orchestrator bridge (1120-1822), and a github glue tool (2036-2049); split into tool-resolution, subagent-session, and planner-wiring modules.
- [severity: med] [category: arch] `run-loop-adapter.ts:1354-1772` — the worker / self-review / ci-fix / reviewer bridges each repeat the same ~60-line setup litany (usage sink, memory index, transcript begin/resume, heartbeat sink, composeStepFinish, streaming renderer, onRetry, providerOptions, conditional-spread pyramid); four real callers of an unextracted `buildSubagentSession` abstraction.
- [severity: med] [category: arch] `run-loop-adapter.ts:2036-2049` vs `src/tools/github-thread-tool.ts` — two implementations of the same `github` review-thread tool with different signatures and divergent validation (the adapter copy posts `input.body ?? ''` — empty replies allowed; the tools copy rejects an empty body with `{ok:false}`); merge-flow-adapter.ts:31 uses one, run-loop-adapter.ts:1255 the other — delete the adapter-local copy.
- [severity: med] [category: arch] `take-over-flow.ts:364-421` — a hand-rolled CI-fix path duplicating ci-fix.ts's `runFixSession` but without compaction, memory, usage accounting, the `'no-changes'` guard, or coding-tier model selection (uses `workerModel` = role 'worker' instead of `modelForCapability('coding')`): `aitm merge-pr` fixes CI with a different, weaker pipeline than `aitm start` — reuse `runFixSession`.
- [severity: med] [category: arch] `merge-flow-adapter.ts:30` — `localEditTools(checkoutPath)` omits `input.resolved.bashRules`, the background ProcessManager, and `applyHooks`: `aitm merge-pr` subagents silently ignore the bash deny/allow governance (issue #113) and operator PreToolUse/PostToolUse hooks (issue #121) that `aitm start` enforces.
- [severity: med] [category: arch] `take-over-flow.ts:81-116` / `merge-flow-adapter.ts` — no `onUsage`/UsageTracker field anywhere in `TakeOverSubagents` and no budget seam in the flow, so usage reporting and the run-level cost/token ceilings (issue #190) do not apply to `aitm merge-pr` at all.
- [severity: low] [category: arch] `run-loop-adapter.ts:716` — `effectiveConcurrency` is hardcoded to `1`, making WorkLoop's batch dispatch, `checkoutMutex` (mutex.ts), and the `concurrency` dep production-dead machinery maintained only for tests.
- [severity: low] [category: arch] `run-loop-adapter.ts:743,745` — a resume mixes persisted options (`current.options.prPerTask`) with freshly-resolved CLI flags (`input.resolved.autoMerge`, `selfReview`, `mergeMethod`); rerunning with different flags half-applies them to a resumed plan with no warning.
- [severity: low] [category: arch] `work-loop.ts:341-343` vs `run-loop-adapter.ts:269-271` — `describeError` duplicated verbatim (same doc comment) in two loop modules; two real callers merit the shared util the house rules call for.
- [severity: low] [category: arch] `work-loop.ts` (1320 LOC) — WorkLoop mixes the batch driver, stage dispatch, the entire prPerTask mode (`processGroup`/`openAndMaybeMerge`, lines 532-1037), outcome accounting, and delivery-merge helpers; prPerTask is a second reason to change and splits cleanly.

## Portability / house rules

- No `Bun.*` APIs, no `any`, no `as unknown as`, no default exports anywhere in `src/loop/` (grep-verified) — compliant. Minor note: `self-review.ts:338` runs verify via `sh -c` (POSIX-only shell, but runtime-portable across Bun/Node/Deno per the house rule's scope).

## Missing capabilities worth adding

- **Deep cooperative cancellation** — thread the AbortSignal through stage handlers, `waitForChecks` polling, grace sleeps, and subagent generate calls so SIGINT cancels in seconds; today the only checks are at WorkLoop batch boundaries and take-over iteration tops.
- **Mid-group budget checkpoints** — cost/token ceilings are consulted only before dispatching a group batch (and never in merge-pr); a single group's task loop + CI-fix cycles can burn unbounded spend between checks. Check per task and per fix pass.
- **Unified start/merge-pr recovery pipeline** — route the take-over flow through `runFixSession` and a shared `freshThreads` dedup so both commands get the same no-changes guard, addressed-thread termination, tolerated-check handling, usage accounting, and fix-attempt cap.
